## 0. 30초 요약

> "영상에서 개인정보 후보를 찾는 부분은 Gemini VLM이, 실제 모자이크를 칠하는 부분은 로컬 YOLO11-seg와 추적기가 담당합니다. VLM에는 영상 전체가 아니라 **균등 8장에 장면 전환·움직임 피크 프레임을 더해 최대 20장의 정지 이미지**를 각각 한 번씩 보냅니다. 분석은 후보를 찾는 단계이고, 렌더링은 그 결과를 시간축으로 보간해 **전 프레임**에 적용합니다. 그래서 렌더 단계에서는 VLM을 다시 호출하지 않습니다."

## 1. VLM에 프레임을 어떻게 보내는가 (정확한 경로)

### 1.1 먼저 정정할 표현

"프레임 단위로 영상을 보낸다"는 표현은 정확하지 않습니다. 정확히는:

- 영상 파일을 통째로 보내지 **않습니다**.
- 전 프레임을 보내지 **않습니다**.
- 영상에서 **균등 6개 + 장면 전환/움직임 피크 최대 6개(합계 최대 16개)**
  프레임을 뽑아, 각각 **JPEG 이미지 1장**으로 만듭니다.
- 프레임마다 **독립적인 API 요청 1회**를 보냅니다. 여러 장을 한 요청에
  묶지 않습니다.
- 즉 VLM은 "영상"이 아니라 **정지 이미지 최대 20장**을 각각 봅니다.

### 1.2 전체 흐름

```text
업로드 MP4
  └─ cv2.VideoCapture
       ├─ 총 프레임 수 N 확인
       ├─ 저해상도(64×36) 서명으로 전체 훑기 → 움직임 변화량 계산
       │    ├─ 컷 검출: 중앙값 + 8×MAD 임계값 초과 지점 (최대 4개)
       │    └─ 움직임 피크: 변화량 국소 최댓값 (최대 3개)
       ├─ 균등 인덱스 4개 + 컷 + 피크 → 최대 16개
       ├─ 순차 seek/read → 프레임들을 메모리에 적재
       └─ ThreadPoolExecutor(max_workers=6)
             ├─ frame 0    → YOLO 사람 검출 → VLM 호출 → JSON 박스
             ├─ frame 300  → YOLO 사람 검출 → VLM 호출 → JSON 박스
             ├─ frame 599  → YOLO 사람 검출 → VLM 호출 → JSON 박스
             ├─ frame 899  → YOLO 사람 검출 → VLM 호출 → JSON 박스
             └─ (컷/피크 프레임) → 같은 처리
                   └─ (선택) 차량 크롭 확대 VLM 최대 2회/프레임
  └─ 결과 병합 → 체크리스트
```

### 1.3 단계별 설명

**① 샘플 프레임 계산 (하이브리드 샘플링)**

`src/sampling.py`의 `plan_samples()`:

```python
plan = plan_samples(video_path, base_count=4, max_count=10)
idxs = plan["indices"]   # 균등 6 + 컷(≤4) + 움직임 피크(≤3)
```

- 먼저 영상 전체를 **64×36 흑백 서명**으로 훑어 프레임마다 움직임
  변화량(평균 절대 차이)을 구합니다.
- **장면 전환(컷)**: 변화량이 `중앙값 + 8×MAD`를 넘으면 컷으로 보고 그
  직후 프레임을 추가합니다(최대 4개).
- **움직임 피크**: 변화량의 국소 최댓값 중 임계값을 넘는 프레임을
  추가합니다(최대 3개). 컷 없는 CCTV에서 사람이 스치는 지점입니다.
- 30초·30fps 영상(900프레임) 기준 균등 샘플은 `0, 300, 599, 899`입니다.
- 결과적으로 **8~20장**이 선택됩니다. 조용한 영상은 8장 그대로,
  컷이 많은 영상은 20장까지 갑니다.

**② 순차적으로 프레임 읽기**

```python
cap.set(cv2.CAP_PROP_POS_FRAMES, idx)
ok, frame = cap.read()
```

- OpenCV `VideoCapture`는 스레드 안전하지 않습니다.
- 그래서 **seek/read는 메인 스레드에서 순차적으로** 수행하고, 읽은 프레임
  비트맵을 메모리에 들고 병렬 처리로 넘깁니다.
- 실제 프레임 위치는 `CAP_PROP_POS_FRAMES - 1`로 보정해 기록합니다.

**③ 6개 워커로 병렬 처리**

```python
with ThreadPoolExecutor(max_workers=parallel_workers) as ex:  # 3
```

- VLM 호출은 네트워크 대기 시간이 길어서 순서대로 보내면 느립니다.
- 6개 워커로 동시에 보내고, 남은 프레임은 먼저 끝난 워커가 처리합니다.
- YOLO 추론 자체는 모델 내부 상태 때문에 `MODEL_LOCK`으로 직렬화하지만, **VLM 네트워크 대기는 겹칩니다**.
- 추가로 **분당 90회 스로틀**을 두어 무료 티어의 분당 한도를 넘기지
  않게 합니다. 429가 나면 25초 대기 후 재시도합니다.

**④ 프레임 1장마다 하는 일**

`src/select.py`의 `VLMSelector.detect_boxes()` → `src/vlm_package.py`의 `detect_with_vlm()`:

1. YOLO11m-seg로 사람 박스/마스크 검출 (`imgsz=960`, `conf=0.20`, `classes=[0]`)
2. VLM에 프레임 1장을 보내 개인정보 후보 박스 요청
3. 필요하면 차량 크롭을 확대해 번호판 전용 VLM 호출
4. 얼굴이 대상이면 YuNet 얼굴 검출 결과를 합집합
5. 사람 박스와 VLM 박스를 IoU로 매칭
6. 번호판/휴대폰 화면처럼 사각형이 명확한 영역은 글자 영역에 맞춰
   박스를 줄임(최소 60% 유지)

**⑤ 이미지 인코딩 (핵심)**

`src/vlm_package.py`의 `_jpg_b64()`:

```python
# 가로가 1920을 넘으면 비율 유지로 축소
if max_w and w > max_w:
    nh = max(1, int(h * max_w / w))
    img_bgr = cv2.resize(img_bgr, (max_w, nh), interpolation=cv2.INTER_AREA)

# JPEG 품질 90으로 압축
ok, buf = cv2.imencode(".jpg", img_bgr,
                       [int(cv2.IMWRITE_JPEG_QUALITY), 90])

# base64 ASCII 문자열로 변환
return base64.b64encode(bytes(buf)).decode("ascii")
```

- 최대 가로 1920px, JPEG 품질 90.
- base64는 원본 바이트보다 약 33% 커집니다.
- 이미지 파일을 업로드하는 게 아니라 **data URL 문자열**로 본문에 넣습니다.

**⑥ API 요청 형식**

```python
image_url = {"url": f"data:image/jpeg;base64,{b64}"}

response = client.chat.completions.create(
    model="gemini-3-flash-preview",
    messages=[
        {"role": "system",
         "content": "당신은 영상 속 개인정보를 탐지하는 전문가입니다. JSON만 출력합니다."},
        {"role": "user", "content": [
            {"type": "text", "text": prompt},
            {"type": "image_url", "image_url": image_url},
        ]},
    ],
    max_tokens=8192,
    temperature=0,
    timeout=90,
    reasoning_effort="low",   # Gemini에만 적용
)
```

- 엔드포인트: `https://generativelanguage.googleapis.com/v1beta/openai/`
- Gemini의 **OpenAI 호환 API**를 사용합니다.
- `temperature=0`: 같은 입력에 최대한 일관된 JSON을 받기 위해.
- `max_tokens=8192`: JSON이 중간에 잘리는 것을 줄이기 위해.
- `reasoning_effort="low"`: Gemini 3가 내부 추론에 출력 토큰을 먼저 쓰면서 JSON이 잘리는 문제를 줄이기 위해.
- `timeout=90초`: 한 프레임 호출의 상한.

**⑦ 응답 파싱과 좌표 복원**

VLM은 대략 이런 JSON 배열을 돌려줍니다.

```json
[
  {"category": "license_plate", "box_2d": [420, 310, 465, 520], "confidence": 0.91},
  {"category": "face", "box_2d": [210, 180, 290, 250], "confidence": 0.87}
]
```

- Gemini는 `box_2d`를 `[ymin, xmin, ymax, xmax]`, **0~1000 정규화**로 주는 경우가 많습니다.
- 코드는 `[xmin, ymin, xmax, ymax]`로 재정렬한 뒤 `w/1000`, `h/1000`을 곱해 원본 픽셀로 바꿉니다.
- `bbox`가 0~1 정규화면 `w`, `h`를 곱합니다.
- 픽셀 좌표로 오면 그대로 쓰되, 전송 전에 축소했다면 `scale = 원본폭 / 전송폭`을 곱해 복원합니다.
- `plausible_box()`로 번호판이 지나치게 세로로 길다거나, 얼굴이 화면 전체를 덮는 식의 **비현실적 박스는 버립니다**.
- JSON이 깨졌으면 완전한 객체만 salvage하거나 재시도합니다.

**⑧ 번호판 보조 호출 (선택)**

`src/preview.py`의 `_refine_plates()`:

- YOLO로 차량 후보를 최대 4대 찾습니다.
- 차량 박스에 12% 패딩을 주고, 가로 640~1280px로 확대합니다.
- "이 크롭에서 번호판만 찾으세요"라는 전용 프롬프트로 VLM을 한 번 더 호출합니다.
- **프레임당 최대 2회**, **영상 전체 6회** 예산을 두고, 여러 스레드가 동시에 예약하지 못하도록 원자적으로 관리합니다.
- 찾은 좌표는 원본 프레임 좌표로 역변환합니다.

**⑨ 결과 병합**

- 카테고리별로 박스를 합칩니다.
- IoU 0.45로 중복 박스를 제거합니다.
- `count`는 영상 전체 누적 개수가 아니라 **한 프레임에서 동시에 보인 최대 개수**입니다.
- 사용자가 요청한 항목과 VLM이 추가로 찾은 항목을 분리합니다.
- 요청했지만 못 찾은 항목은 `못 찾음`으로 표시합니다.

### 1.4 1회 분석당 호출 수

| 구분 | 호출 수 |
|---|---|
| 기본 프레임 분석 | 8~20회 (프레임당 1회, 샘플 수만큼) |
| 번호판 확대 | 최대 28회 (프레임당 2회, 영상 전체 28회) |
| **합계** | **최대 48회, 일반적으로 8~20회** |
| 렌더 단계 | **0회** (`RENDER_VLM_CALLS=0`) |
| 분당 제한 | 90회 (스로틀). 초과 시 429 → 25초 대기 후 재시도 |

### 1.5 전송량 감각

- 1920px JPEG q90: 대략 **0.3~1MB/장** (장면 복잡도에 따라)
- base64 +33% → **0.4~1.3MB/요청**
- 20장 기준 대략 **8~25MB**
- 원본 영상 파일, 오디오 트랙은 전송하지 않습니다.

> 교수님께는 이렇게 말하면 됩니다:
> "영상 전체를 보내는 게 아니라, 균등 6장에 장면 전환·움직임 피크 프레임을 더해 최대 16개 프레임을 JPEG로 압축해 base64 data URL로 각각 한 번씩 보냅니다. 프레임당 요청 1회, 번호판 보조까지 포함해 최대 36회입니다."

## 2. 예상 질문 & 답변

### A. 시스템 개요

**Q1. 전체 구조를 설명해 달라.**

> 3단계입니다. ① VLM과 YOLO로 개인정보 후보를 찾는 **분석 단계**, ② 사용자가 가릴 항목을 고르는 **선택 단계**, ③ YOLO 추적과 마스크로 전 프레임을 처리하는 **렌더 단계**입니다. VLM은 "무엇이 개인정보인지"를 판단하고, YOLO는 "사람이 어디 있고 어떤 픽셀인지"를 담당합니다. 역할을 분리해서 VLM 호출은 6~36회로 묶고, 렌더는 로컬 GPU에서 처리합니다.

**Q2. 왜 VLM을 썼나? YOLO만으로 안 되나?**

> 얼굴·번호판처럼 형태가 일정한 것은 YOLO로도 가능하지만, 주소 간판·명찰·신분증·휴대폰 화면·"초록 옷 입은 사람" 같은 자유 형식 요청은 고정 클래스로 정의하기 어렵습니다. VLM은 자연어 지시와 문맥을 이해해서 후보를 찾을 수 있습니다. 다만 VLM은 좌표가 매 프레임 안정적이지 않고 비용도 들기 때문에, 사람 마스크와 시간적 추적은 YOLO11-seg가 맡습니다.

**Q3. VLM이면 다 되는데 왜 YOLO도 쓰나?**

> VLM은 8~20장만 보고, 박스 좌표가 프레임마다 흔들립니다. 실제 모자이크는 전 프레임에 안정적으로 칠해야 하므로 사람의 픽셀 마스크와 추적이 필요합니다. YOLO11-seg는 사람 마스크를 픽셀 단위로 주고, ByteTrack으로 시간적 일관성을 유지합니다. 비용과 속도 면에서도 분석과 렌더를 분리하는 게 유리합니다.

### B. 프레임 / VLM

**Q4. 프레임을 몇 장 보내나?**

> 균등 8장을 기본으로 하되, **장면 전환과 움직임 피크를 더해 최대 20장**을
> 보냅니다. 영상 전체를 64×36 서명으로 훑어 화면이 크게 바뀐 지점(컷)과
> 움직임 변화량이 국소 최댓값인 지점(사람이 스치는 순간)을 찾아 그
> 프레임을 추가합니다. 10초 영상에서 2.2초에만 신분증이 스치면 균등 6장
>으로는 놓치지만, 컷/피크 샘플링은 잡아냅니다. 조용한 영상은 6장 그대로
> 두어 불필요한 호출도 안 만듭니다. 그래도 모든 순간을 커버할 수는 없어서
> 분석은 "후보 발견"으로 한정하고 렌더 단계에서 추적·보간으로 보완합니다.

**Q5. 구체적으로 어떤 형식으로 보내나?**

> 프레임을 최대 가로 1920px로 줄이고 JPEG 품질 90으로 압축한 뒤 base64로 인코딩합니다. OpenAI 호환 `image_url` 메시지에 `data:image/jpeg;base64,...` 형태로 넣습니다. 파일 업로드가 아니라 요청 본문에 포함되는 문자열입니다. 프레임 1장당 요청 1회이고, 여러 장을 한 요청에 묶지는 않습니다.

**Q6. 샘플 몇 장만 보고 전체 영상을 어떻게 처리하나?**

> 분석과 렌더를 분리했습니다. 분석은 "이 영상에 어떤 개인정보가 나오는지" 후보 목록을 만드는 단계이고, 렌더는 15프레임 간격의 키프레임에서 YOLO 추적을 돌리고 그 사이를 보간하는 단계입니다. 즉 VLM이 찾은 박스를 시간축 prior로 쓰고, 실제 전 프레임은 로컬 추적이 커버합니다. 짧게 등장하는 객체는 놓칠 수 있다는 한계는 있습니다.

**Q7. VLM이 준 좌표를 어떻게 원본 영상 좌표로 바꾸나?**

> Gemini는 `box_2d`를 `[ymin, xmin, ymax, xmax]` 0~1000 정규화로 주는 경우가 많아서, `[xmin, ymin, xmax, ymax]`로 재정렬하고 `w/1000`, `h/1000`을 곱합니다. 0~1 정규화와 픽셀 좌표도 처리합니다. 전송 전에 이미지를 축소했다면 픽셀 좌표에 축소 비율을 곱해 복원하고, 비현실적인 크기·비율의 박스는 필터로 버립니다.

**Q8. 작은 번호판은 어떻게 찾나?**

> 전체 프레임에서 VLM이 놓치면, YOLO로 차량을 찾아 크롭하고 12% 패딩을 준 뒤 640~1280px로 확대해서 "번호판만 찾으세요"라는 전용 프롬프트로 한 번 더 호출합니다. 프레임당 2회, 영상 전체 28회로 예산을 제한해 비용이 폭증하지 않게 했습니다. 찾은 좌표는 원본 좌표로 되돌립니다. 추가로 VLM이 번호판 박스를 너무 넓게 잡으면 글자가 실제로 있는 영역으로 줄여 모자이크가 번지는 것을 막습니다.

**Q9. 얼굴이 VLM에서 누락되면?**

> 사용자가 얼굴을 선택하면 렌더 단계에서 OpenCV YuNet 얼굴 검출을 프레임마다 돌려 보강합니다. VLM 결과와 합집합으로 처리합니다. 얼굴만 선택한 경우에는 얼굴 박스만 타원형으로 가려서 목·상체까지 번지지 않게 합니다. YuNet조차 놓치는 프로필/고개 숙인 얼굴은 사람 박스의 머리 영역을 가리는 fallback 으로 한 번 더 보완합니다.

**Q10. VLM이 없는 개인정보를 만들어 내면(환각)?**

> 좌표가 비현실적이면 `plausible_box()`로 버리고, 최소 크기 미만도 버립니다. 사람 박스와의 IoU 매칭을 통과해야 하며, 최종적으로 사용자가 체크리스트에서 확인하고 선택합니다. 자동으로 전부 가리는 구조가 아니라 **사용자 통제**를 두었기 때문에 오탐이 바로 결과에 반영되지 않습니다. 다만 100% 완벽한 판정은 아니라고 말하는 게 정직합니다.

**Q11. 영상 전체가 Google로 가나? 개인정보 보호 서비스인데 아이러니하지 않나?**

> 영상 전체나 오디오는 가지 않습니다. 샘플 최대 20장과 선택적 차량 크롭 이미지만 전송합니다. 통신은 HTTPS이고, 원본 영상은 서버 임시 폴더에서만 처리합니다. 다만 외부 VLM API를 쓰는 구조라서 "완전한 온디바이스"는 아닙니다. 민감도가 높은 영상은 OpenAI 호환 로컬 VLM으로 교체할 수 있게 `base_url`을 분리해 두었고, 이게 향후 과제입니다. 이 질문은 숨기지 말고 한계로 인정하는 게 좋습니다.

**Q12. 왜 매 프레임 VLM을 호출하지 않나?**

> 30fps·1분 영상이면 1,800회 호출이 되어 비용과 지연이 선형으로 폭증합니다. Rate limit도 걸리고, VLM 좌표는 프레임마다 흔들려서 그대로 쓰기 어렵습니다. 그래서 VLM은 후보 발견에만 쓰고, 전 프레임은 로컬 추적과 보간으로 처리합니다. 렌더 단계 VLM 호출은 0회입니다.

**Q13. 비용과 시간은?**

> 분석 1회당 VLM 호출이 기본 8~20회, 번호판 보조 최대 28회, 합계 최대 48회입니다. Modal L4는 시간당 대략 0.6달러 수준이고 월 30달러 크레딧을 쓰며, 5분간 접속이 없으면 컨테이너가 내려가 과금이 멈춥니다. Gemini 쪽은 이미지 수와 토큰 종량 과금이라 영상 길이보다 "분석 횟수"에 비례합니다. 렌더 시간은 영상 길이와 해상도에 비례합니다.

### C. 렌더링

**Q14. 모자이크는 어떻게 칠하나?**

> 사람은 YOLO11-seg의 세그멘테이션 마스크 안쪽에만 모자이크를 적용합니다. 배경 개인정보(번호판·간판 등)는 VLM 박스를 prior로 쓰고, 번호판은 물체 크기에 비례한 작은 여백만 붙입니다. 모자이크 블록 크기는 ROI 크기가 아니라 **작은 축을 몇 개로 나누는지(기본 약 4.5칸)** 로 계산합니다. 예전처럼 ROI 크기에 비례해 블록을 크게 만들면 얼굴이 몇 개 덩어리로 뭉개져 형태가 사라집니다. 마스크 경계는 안쪽으로만 1~2px 페더링로 부드럽게 만들고, 픽셀 스타일은 하드 경계가 자연스러워 페더링을 생략합니다.

**Q15. 시간축 처리는?**

> 렌더는 15프레임 간격으로 키프레임을 잡고 ByteTrack으로 사람을 추적합니다. VLM이 찾은 배경 박스는 샘플 프레임 사이를 보간하고, 번호판은 물체 크기에 비례한 여백으로 이동 오차를 덮습니다. 얼굴은 YuNet으로 프레임마다 검출하고, YuNet이 놓친 프로필 얼굴은 사람 박스 머리 영역으로 보완합니다. 그래서 VLM이 찾은 박스는 렌더에서 전 프레임에 적용됩니다.

**Q16. 오디오와 출력 포맷은?**

> 원본 오디오를 기본으로 유지하지만, 사이드바의 `오디오 제거`를 켜면 목소리도 제거합니다. 출력은 H.264/yuv420p/faststart MP4이고, 인코딩 프리셋은 veryfast입니다. 브라우저에서 바로 재생되고 다운로드됩니다.

**Q17. 체크를 해제하면?**

> 렌더 요청을 만들 때 선택된 카테고리만 `RenderPlan`에 넣습니다. 해제한 항목은 판정·렌더에서 제외됩니다. "요청한 항목"과 "추가로 찾은 개인정보"를 나눠 보여주고, 요청했지만 못 찾은 항목은 `못 찾음`으로 표시합니다.

### D. 운영 / 배포

**Q18. 로그인과 보안은?**

> 앱 진입 시 로그인을 요구하고, 계정은 SQLite `users.db`에 저장합니다. 비밀번호는 PBKDF2-SHA256 20만 회 + 사용자별 salt 해시로만 저장하고 평문은 저장하지 않습니다. 5회 연속 실패하면 SQLite에 아이디 기준으로 기록되어 60초 잠깁니다(탭을 새로 열어도 유지). 결과와 `지난 작업`은 로그인한 아이디별로 분리됩니다. Gemini 키는 Modal **Named Secret**(`mosaic-gemini`)으로만 주입하고, 이미지·저장소·로그에는 남기지 않습니다. Named Secret은 워크스페이스에 있어 배포 PC마다 키를 복사할 필요가 없습니다.

**Q19. 왜 Modal인가? GPU는 어디에 쓰나?**

> 다른 컴퓨터에서 접속하려면 HTTPS 공개 주소가 필요한데, Modal은 배포하면 자동으로 HTTPS URL과 WebSocket을 지원하고 접속이 없으면 0으로 줄어드는 scale-to-zero를 제공합니다. L4 GPU는 YOLO11-seg 추론·추적·인코딩에 쓰고, VLM 자체는 Gemini API가 처리합니다. 즉 GPU가 VLM을 돌리는 건 아닙니다.

**Q20. 동시 접속은?**

> Streamlit 세션은 여러 명이 동시에 열 수 있고, Modal 쪽은 `max_inputs=100`으로 받습니다. 다만 SQLite와 모델 상태 일관성을 위해 컨테이너는 1개만 띄웁니다. 미리보기 YOLO 추론은 `MODEL_LOCK`으로 직렬화되고, 무거운 렌더가 겹치면 L4를 공유하므로 느려질 수 있습니다. 대규모 동시 사용자는 컨테이너 분리와 작업 큐가 필요합니다.

**Q21. API 오류는 어떻게 처리하나?**

> 키가 없으면 분석을 시작하지 않고 안내합니다. 일일 한도(하루 총량)는 재시도해도 소용없으므로 즉시 중단하고 사용자에게 알립니다. 401/403(인증), 모델 없음도 동일합니다. **분당 한도(429)는 잠시 기다리면 풀리므로 25초 대기 후 재시도**하고, 그 전에 90회/분 스로틀로 호출 자체를 천천히 분산합니다. 5xx 서버 오류와 JSON 파싱 실패도 최대 3회 재시도합니다. 한 샘플에서 치명적 오류가 나면 `Event`로 대기 중인 나머지 샘플 호출을 취소해 불필요한 과금을 막습니다. JSON이 잘리면 완전한 객체만 salvage합니다.

**Q22. 데이터는 얼마나 보관하나?**

> 원본은 임시 폴더에서만 처리하고, 결과는 `outputs/`에 저장합니다. 기본 24시간이 지난 결과는 앱 시작 시 자동 정리되고, 다운로드 시 즉시 삭제하는 옵션도 있습니다. 계정과 결과는 Modal Volume에 있어 재배포해도 유지됩니다.

### E. 한계 / 개선

**Q23. 이 시스템의 한계는?**

> 첫째, 샘플이 최대 20장이라 아주 짧게 등장하는 개인정보는 여전히 놓칠 수 있습니다. 둘째, 외부 VLM API에 샘플 이미지가 전송되므로 민감 영상에는 온디바이스 대안이 필요합니다. 셋째, 단일 컨테이너라 대규모 동시 사용에는 한계가 있습니다. 넷째, 아직 mAP/F1 같은 정량 벤치마크가 아니라 스크립트 기반 회귀 테스트 중심입니다. 다섯째, 음성 내용을 인식해 일부만 지우지는 못하고 오디오 전체 제거만 지원합니다.

**Q24. 개선 방향은?**

> 이미 구현한 것이 있습니다. ① 장면 전환 + 움직임 피크 기반 하이브리드 샘플링(최대 20장), ② YuNet이 놓친 프로필 얼굴의 머리 영역 fallback, ③ 번호판 박스 자동 조임과 여백 축소. 앞으로는 로컬 VLM으로 프라이버시를 강화하는 방법, 음성 구간을 함께 가리는 방법, 컨테이너를 분리하고 작업 큐를 두는 방법, 라벨링 데이터셋으로 정량 평가하는 방법이 있습니다. 수동 영역 추가/제외 UI와 검출 박스·추적 ID를 보여주는 디버그 영상은 이미 구현했습니다.

**Q25. 정량 평가는 했나?**

> 기능 검증은 `pytest tests`(22개), `smoke`, `authtest`, `checklist`, `qualitytest`, `sampletest`, `freeform`, `regression`, `robustness`, `apptest`, `golden_run` 25개 시나리오로 했습니다. 모자이크 후 얼굴 재검출을 세는 `leak_metrics.py`도 추가했습니다. 다만 탐지 정확도를 mAP나 F1으로 수치화하지는 않았습니다. 발표에서는 "기능 검증은 완료, 정량 벤치마크는 향후 과제"라고 말하는 게 정확합니다.

### F. 비교 / 설계 선택

**Q26. 기존 자동 모자이크 제품과 차별점은?**

> 기존 제품은 검출된 개인정보를 자동으로 전부 가리는 경우가 많습니다. 이 앱은 ① 후보를 체크리스트로 보여주고, ② 사용자가 가릴 항목만 고르며, ③ "얼굴과 번호판만" 같은 자연어 요청과 추가 발견 항목을 함께 제시합니다. 불필요한 모자이크를 줄이고 사용자가 최종 통제권을 갖는 것이 차별점입니다.

**Q27. 왜 Streamlit인가?**

> Python만으로 업로드·비디오 재생·다운로드·세션 상태를 빠르게 만들 수 있어서 프로토타입에 적합합니다. 반면 대규모 동시성이나 복잡한 UI에는 한계가 있어서, 실제 서비스라면 프론트/백엔드 분리가 필요합니다.

**Q28. 실시간인가?**

> 아닙니다. 업로드 후 분석하고 버튼을 눌러 렌더하는 배치 구조입니다. 실시간 스트리밍을 하려면 프레임 파이프라인, 경량 모델, 지연 최적화가 별도로 필요합니다.

**Q29. 모델명이 preview인데 운영에 써도 되나?**

> `VLM_MODEL` 환경변수로 교체할 수 있게 분리했습니다. preview 모델은 품질·비용을 실험하기 위한 선택이고, 운영에서는 GA 모델로 고정하는 것이 맞습니다. 다만 모델이 바뀌면 JSON 형식과 좌표 스케일이 달라질 수 있어 회귀 테스트가 필요합니다.

**Q30. 키가 코드나 저장소에 남지 않나?**

> 아닙니다. 실제 키는 Modal Named Secret(`mosaic-gemini`)에만 있고, 저장소·이미지·로그에는 남지 않습니다. 배포할 때 `modal.Secret.from_name("mosaic-gemini")`로 참조하므로, 키를 들고 있는 PC 말고도 Modal 로그인만 되어 있으면 배포할 수 있습니다. 앱에는 키 입력창이 없고, 화면·로그에 키를 출력하지 않습니다.

## 3. 까다로운 꼬리 질문 대비

**"6장이면 충분한가?"**

> 그래서 더 이상 균등 6장만 보지 않습니다. 영상 전체를 저해상도 서명으로 훑어 **장면 전환 지점**과 **움직임 피크 지점**을 찾고, 균등 6장에 컷·컷 직전·피크 최대 10장을 더해 최대 16장을 VLM에 보냅니다. 10초 영상에서 2.2초에만 스친 신분증도 잡힙니다. 그래도 모든 순간을 커버할 수는 없어서 분석은 후보 발견으로 한정하고, 렌더는 15프레임 키프레임 추적과 보간으로 전 프레임을 커버합니다.

**"개인정보 보호 서비스가 개인정보를 구글에 보내는 게 맞나?"**

> 영상 전체가 아니라 샘플 최대 20장과 선택적 차량 크롭만 보냅니다. 원본 영상과 오디오는 전송하지 않습니다. 다만 외부 API 의존은 분명한 한계이고, 민감 영상용으로 로컬 VLM 대안을 열어 두었습니다.

**"VLM이 좌표를 안 주면?"**

> `box_2d`, `bbox`, `xyxy`를 모두 처리하고, 좌표가 없거나 4개가 아니면 그 항목은 버립니다. JSON 자체가 깨지면 완전한 객체만 salvage하거나 재시도합니다. 좌표 없는 텍스트 설명만으로는 모자이크를 칠하지 않습니다.

**"얼굴 인식(누구인지)도 하나?"**

> 아닙니다. 얼굴을 **검출**해서 가릴 뿐, 신원을 식별하지 않습니다. 개인정보 보호 목적에 필요한 최소 기능만 합니다.

**"음성도 가리나?"**

> 아닙니다. 기본은 시각적 개인정보만 자동 처리하고 원본 오디오를 유지합니다. 다만 `오디오 제거` 옵션으로 목소리 트랙을 통째로 뺄 수 있습니다. 음성 내용을 인식해 특정 단어만 지우는 기능은 향후 과제입니다.

**"왜 여러 장을 한 요청에 안 보내나?"**

> 프레임별로 좌표를 명확히 grounding하기 위해서입니다. 한 요청에 여러 장을 넣으면 어느 박스가 어느 프레임인지 섞일 수 있고, 부분 실패 시 재시도 단위도 커집니다. 프레임당 요청을 분리하면 병렬화와 오류 격리에 유리합니다.

**"GPU가 없으면 안 되나?"**

> 동작은 가능하지만 느립니다. YOLO11-seg 추론·추적·인코딩이 CPU에서는 병목이 됩니다. L4는 이 부분을 가속합니다. VLM은 외부 API라서 GPU와 무관합니다.

**"오픈 회원가입이면 아무나 크레딧을 쓰는 것 아닌가?"**

> 맞습니다. 초대 코드(`MOSAIC_INVITE_CODE`)를 Secret에 설정하면 코드를 아는 사람만 가입할 수 있습니다. 설정하지 않으면 주소를 아는 사람이 가입할 수 있어 팀 내부 공유를 전제로 합니다. 이메일 도메인 제한·관리자 승인은 추가로 고려할 수 있습니다.

## 6. 장면 전환 기반 샘플링 (구현됨)

### 한 줄 정의

영상 전체를 균등하게 4등분하는 대신, **화면이 크게 바뀌는 지점(컷/장면 전환)을 찾아 그 전후를 우선 샘플링**하는 방식입니다. 여기에 **움직임 변화량 피크**를 더했습니다.

### 왜 필요한가

`np.linspace(0, N-1, 4)`는 영상 내용과 무관하게 위치만 균등합니다.

- 10초 영상에서 2.2~2.5초에만 신분증이 스치면, 0 / 3.3 / 6.6 / 9.9초 샘플에는 안 잡힙니다.
- 반대로 10초 내내 같은 장면이면 6장이 거의 동일해서 VLM 호출이 낭비됩니다.

### 어떻게 동작하나 (구현: `src/sampling.py`)

1. 영상 전체를 **64×36 흑백 서명**으로 훑습니다(최대 900프레임).
2. 이전 서명과의 평균 절대 차이 = **움직임 변화량**을 구합니다.
3. **컷**: 변화량이 `max(18, 중앙값×5, 최고값×0.45, p98)`을 넘으면
   장면 전환으로 보고 **직후 프레임**을 샘플에 추가합니다(최대 4개).
4. **움직임 피크**: 변화량의 국소 최댓값(±2프레임) 중
   `max(1.0, 중앙값×2, 최고값×0.35)`을 넘는 프레임을 추가합니다(최대 3개).
   컷 없는 CCTV에서 사람이 스치는 지점을 잡습니다.
5. 균등 8장 + 컷 + 피크 = **최대 20장**. 조용한 영상은 8장 그대로 둡니다.
6. 선택된 샘플은 6개 워커로 병렬 VLM 호출됩니다.

> 임계값을 영상마다 중앙값/MAD로 정하는 이유는 **카메라 흔들림을 컷으로
> 오탐하지 않기 위해서**입니다. 절대값 임계값(고정 45)만 쓰면 흔들리는
> 영상에서 컷이 과다 검출됩니다.

### 장단점

- 장점: 짧게 등장하는 개인정보를 잡을 확률이 올라가고, 중복 샘플이 줄며,
  정지된 화면에서는 호출을 아낍니다.
- 단점: VLM 호출 수가 늘고(최대 36회), 임계값 튜닝이 필요하며,
  카메라 흔들림·조명 변화를 컷으로 오탐할 수 있습니다. 컷이 없는 영상은
  움직임 피크에만 의존합니다.
- 그래서 **총 샘플을 20장으로 상한** 두고, 분당 90회 스로틀로 무료 티어
  한도도 지킵니다.

### 교수님 답변

> "장면 전환 기반 샘플링은 영상 내용이 크게 바뀌는 지점을 찾아 그 주변을 우선 샘플링하는 방식입니다. 현재는 균등 8장에 컷 최대 4장, 컷 직전 최대 2장, 움직임 피크 최대 4장을 더해 최대 20장을 VLM에 보냅니다. 임계값은 영상마다 중앙값 기준으로 적응적으로 정해 카메라 흔들림을 컷으로 오탐하지 않게 했고, 총 샘플 수와 분당 호출 수를 상한으로 묶어 비용을 예측 가능하게 유지했습니다. 덕분에 균등 샘플이 놓치던 짧게 스친 개인정보를 잡습니다. 다만 아무리 늘려도 모든 순간을 커버할 수는 없어 분석은 후보 발견으로 한정하고, 렌더 단계의 추적·보간으로 전 프레임을 커버합니다."
